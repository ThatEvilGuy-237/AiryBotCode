# Airy panel review: R2 (shell, sign-in, Home)

Surface: operator tool (the owner and his mods run Discord bots). Kit rules apply as written
(mono for ids/counts/times, 24 px desktop hit-target floor, no 16 px-field rule). Judged from
rendered evidence only: `docs/screenshots/r2-home*.png`, `r2-home.json`, `r2-home-grouped-*`,
`r2-home-states-*`, `r2-menu-375.png`, `r2-signin-*.png`, `r2-login-1440.png`.

## Interactions and feedback seen

Switch bot (select) -> name, avatar, id and stats update; busy/dim treatment during reload could
not be confirmed from a still frame. Sidebar nav -> selected item gets a filled row and left
accent bar (Home, every shot). Sign-in password -> Continue disabled (muted teal, dark text)
until text is entered, then full sky blue; wrong password reddens the field border and prints an
inline mono error; step 2 shows a "Sign in with Discord" primary plus a quiet "Back". Phone menu
-> one sliding sidebar, same nav as desktop, shown focused with a visible ring (`r2-menu-375.png`).
Stat tiles (Channels, Commands on, Suggestions, Counting record) are each a full-card link. Empty
and error states (no bots, bots failed, no channels, no Hive) each carry one primary CTA to the
page that fixes them. All of this works and is visible feedback, not assumed.

## Blocks: does the usual case need this here

Header (avatar, name, mono id, ON pill), stat strip, "Where Airy talks" card: yes, matches the
brief's "which bot, what runs, what needs a look" job. No session card, no ping button, no bot
list block: confirmed absent, correct. The "needs a look" block itself is conditional (only shown
when something is wrong) in every capture, but no capture shows a fully healthy bot with zero
problems, so the "block disappears when nothing is wrong" claim in the brief is unverified, not
confirmed working; call this out rather than wave it through.

## Findings

### High

1. **Bot switcher renders empty with a stale avatar** — `r2-home-states-no-bots-1440.png`,
   `r2-home-states-bots-failed-1440.png` (confirmed by a 4x crop of the switcher region). With no
   bot selected, the select box shows no text at all (not even a placeholder) while the avatar
   circle to its left still shows a previous bot's artwork. This reads as broken, not as an empty
   state. Fix: when there is no selected bot, show a neutral placeholder avatar and a label such
   as "No bot" in the switcher, never a blank control next to someone else's art.

2. **Duplicate "Open channels" alerts instead of one grouped alert** — `r2-home-1440.png`,
   `r2-home-375.png`, `r2-home-320.png` (this is the real Cookie&Creams bot's current live state,
   not a synthetic one) show two full alert cards stacked, each with its own identical "Open
   channels" button, for two problems that both resolve on the same page. `r2-home-grouped-
   grouped-1440.png` / `-375.png` prove the better pattern already exists: three problems are
   merged into one "3 things need a look" alert with a bullet per problem and a single CTA. The
   two-problem case should use the same grouped pattern — two cards repeating the same button
   label is wasted space and reads as a mistake. Fix: group from 2 problems, or whenever multiple
   problems share one destination page.

3. **Axe reports a serious color-contrast violation that contradicts the measured baseline** —
   `r2-home-states-states.json`, state "long-and-broken", viewport 375: `a11y.violations` lists
   one `color-contrast` violation, impact "serious", target `.off > .guild`. The brief's own
   "Measured" line claims axe 0 in every captured state at 375 and 1440; this JSON (generated in
   the same screenshot pass) says otherwise. I could not find the element visually in
   `r2-home-states-long-and-broken-375.png` and could not re-render it live (the capture's dev
   server on :5173 is not currently running to re-probe). Needs a direct look at whatever
   `.off`/`.guild` renders (likely an off/paused channel-server label) before this round is called
   clean.

### Medium

4. **Failure text isn't colour-coded as a failure** — `r2-home-grouped-grouped-1440.png`, the
   `#chat` row: "failed · 1 hour ago" is set in the same neutral grey as a healthy outcome ("yes
   88% · 2 hours ago" on the row above); only a small 6 px dot carries the colour. The brief's own
   colour rule puts failures in danger (red). Fix: colour the outcome word itself for a failed
   check, not only the status dot.

5. **Loading feedback is inconsistent on one page** — `r2-home-states-loading-1440.png`: the stat
   strip shows a static "…" placeholder while "Where Airy talks" shows animated skeleton bars,
   two different loading conventions on the same screen. Brief calls for "Skeleton rows" for Home
   loading. Fix: give the stat tiles the same Skeleton treatment instead of an ellipsis.

6. **375 "loading" capture shows the sign-in card, not a Home skeleton** —
   `r2-home-states-loading-375.png` (same frame appears as panel 5 of `r2-home-states-sheet.png`)
   is pixel-identical to the plain sign-in screenshot, while the 1440 capture of the same named
   state correctly shows the shell with stats "…" and skeleton rows. Either this is a different,
   earlier "determining session" phase that happens to share the state name, or the Home loading
   skeleton is missing at phone width. Needs confirmation either way before sign-off.

### Low / Nit

7. **Progress bar does not distinguish done from current on step 2** — compare
   `r2-signin-375.png` (step 1: one filled sky segment, one muted grey) to
   `r2-signin-discord-375.png` (step 2: both segments identical sky blue). With only two steps the
   effect is minor (step 2 is also the last step), but it does not follow the done/current/
   remaining colouring the rule calls for. Low priority given the two-step case.

## Measured, explained, not counted as new findings

- The 13-14 probe boxes on `r2-home-1440.png` / `r2-home.json` (sidebar nav items 238x32, "Open
  channels" 120x28, "Change" 62x32, "Sign out" 101x28, the bot switcher 155x36) are desktop hit
  targets of 28-36 px, above this tool's 24 px desktop floor; the 16 px field-text rule is a phone
  rule and does not apply here. Correctly not failing axe (0 violations, 1440 and 320).
- The probe's reported "name" for the bot-switcher small-target entry ("No bots yet\ndevairybot\nA")
  is the raw concatenated `<option>` text of the native select, not its real accessible name. The
  accessibility tree for the same control (`r2-home-states-states.json`, "long-and-broken",
  1440) shows `combobox "Bot" [expanded=false]: Cookie&Creams` with the correct option list and
  the right one marked `[selected]`. Not a defect.
- The boxed-off channel emoji in `r2-home-375.png` / `r2-home-320.png` is a headless-browser font
  gap, already flagged as expected in the task brief. Not a defect.

## Cannot be judged from this evidence

- Whether the "needs a look" block truly disappears for a bot with zero problems (no capture shows
  that state).
- The "busy dim" during a bot switch (`r2-home-switch-1440.png` is a still frame; cannot confirm a
  transient dim/overlay effect existed and was simply over by capture time).
- Whether truncated long names/server names (`r2-home-grouped-grouped-1440.png`,
  "#a-very-long-channel-name-for-the-community-anno…", "Cookies&Cream Audios with a long server
  na…") carry the full string in a `title` attribute as the brief requires; not visible in a
  screenshot or the probe JSON.
- Recall, discoverability and whether mods will actually find "Open channels" useful day to day:
  unjudgeable from screenshots.

## The open choice: should the bot's image recolour the panel

No. Keep one identity. The brief's own default ("proposed no") is correct per the standing rule
that one mark and one palette carry every surface and hand-off page (sky on navy, the cloud mark);
letting an uploaded bot avatar repaint accents would make the "one accent" promise conditional on
whatever image a mod uploads, and would break recognisability for the owner switching between
multiple bots in the same sidebar session, which this panel's whole job is built around (switch
bot, see what's wrong, go fix it). The avatar staying scoped to "this is the bot's own picture" is
also what makes finding #1 above visible as a bug rather than a feature: the avatar carrying no
identity weight is exactly why a stale one sitting next to an empty switcher reads as broken.
