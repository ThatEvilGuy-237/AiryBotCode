The owner's ask ("pick a channel, not just add an id; it shows the name; picking one is better")
is met and is now consistent everywhere a channel is chosen: Channels' "Find a channel" add-row,
and Settings' Log channel / Owner log channel, all use the same search field, both render

"memes") groups results under a mono server-name header per server and bold-highlights the typed

## Interactions and feedback seen

Command row switch (Commands) -> fills sky blue at once (`r4-commands-1440.png`: "Contact a
user"/"Counting" on, eight off). Row click -> right-side editor panel opens in place
(`r4-editor-1440.png`), its own footer tracks dirty state in words ("No changes" ->
`r4-editor-changed-1440.png` "1 changed", "Save" goes from muted to full sky blue). Channel search
-> dropdown opens on focus grouped by server, typed text bold-highlighted in each result
(`r3-picker-open-1440.png`, `r3-picker-search-1440.png`); "Add channel" stays disabled/muted until
a channel is chosen. Channel row Pause -> switch and "Remove" sit at 36x20 visually but the
probe's real hit rectangle is 44x28 (`r4-channels.json`, target "Airy talks in #airy-talk"), above
the 24 px desktop floor — this is R3 High #1 ("Pause switch is a 20 px target"), now fixed. Look
colour pick -> ring on the chosen swatch, "Save the look" disabled only becomes primary after the
page clearly shows a picking state; save confirms with a bottom-right toast, green left accent,
"Look saved" plus an inline "Use as Discord avatar" action pill (`r4-look-saved-1440.png`),
matching the toast pattern from R3.

## Findings

### Blocker

1. **Picking Look colours silently destroys the bot's real avatar picture** —
   `r4-look-1440.png` "Now" shows the bot's actual custom Discord avatar (a round K-pop "Demon
   Hunters" image) with derived colours `#11213b` / `#040613`. `r4-look-pick-1440.png` ("How it
   will look" / "Pick the colours") shows the *same* preview slot now rendering Airy's generic
   product mascot (the plain blue cloud-robot glyph used for the fixed "Airy" wordmark logo) with
   both Message colour and Second colour set to the brand's own `#38bdf8` — and there is no "New
   picture" section anywhere on this screen, so no file was dropped or chosen as part of this
   flow. `r4-look-saved-1440.png` confirms the loss is not just a preview artefact: after "Save
   the look" the generic mascot is now the bot's avatar in "Now" *and* in the sidebar bot switcher
   (compare against the same switcher showing the real custom picture on `r4-commands-1440.png`,
   `r4-settings-1440.png`, and the Look page's own un-edited state — crops in `/tmp/look1440_sidebar.png`
   vs `/tmp/looksaved1440_sidebar.png`). The page's own job, per the brief, is "the bot's image,
   the colours taken from it, set as avatar" — colours should derive from the picture, not replace
   it. This is the exact shape of silent data loss the project has hit before (editing a webhook
   without retyping its secret erases the secret). Fix: the colour picker must never touch the
   stored avatar image; only writing a new picture (drop or "choose one") may change it, and any
   action that resets the picture needs its own explicit, named confirmation.

### High

2. **The sticky Save/Undo bar covers Admin roles and the Owner's Discord user id at page load** —
   `r4-settings.json`, 1440, `probe.targets`: four controls report `"hit": [1, 1]` with
   `"coveredBy": "div.bar"` — the "Remove @Moderator" chip (13x13), the Admin roles combobox input
   (202x22), its own clear control (14x14), and the Owner's Discord user id textbox (511x41,
   `r4-settings-1440-findings.png` boxes #31-#34). `probe.overlap` additionally shows the id
   value's own text, `405431299323461634`, physically overlapping the "Undo changes" (area 4034 px²)
   and "Save" (area 1507 px²) buttons at `rect [1140/1284, 852, …]`. This is the page's resting,
   unscrolled state at the standard 1440x900 viewport this review series probes at — not a far
   scroll edge case. An operator opening Settings cannot click into Admin roles or type an owner id
   without first discovering they need to scroll past where the content visually already stops.
   Fix: reserve bottom padding on the scrollable content equal to the sticky bar's height so no
   field's hit area is ever zeroed out by `div.bar`.

### Medium

3. **Modal/drawer backdrop still doesn't suppress the page behind it** — carried over from R3
   Medium #2, now reproduced on the Commands settings editor. Pixel sampling: at 1440 the page
   background goes from `#0F1722` to `#090D14` under the drawer (`r4-commands-1440.png` vs
   `r4-editor-1440.png`, same coordinate); at 375 the page background goes from `#050A11` to
   `#02050A`/`#020509` (`r4-commands-375.png` vs `r4-editor-375.png`). Both are a partial darken,
   not a kill: the "Commands" heading, card borders, and row text remain clearly legible through
   the scrim in both crops (`/tmp/editor375_left2.png` vs `/tmp/commands375_left.png`). The brief
   already logged two other Modal defects fixed this round elsewhere; this one is still open. Fix:
   raise scrim opacity well past legibility or add a backdrop blur.

4. **Settings' Database field is one flat list of every database on the shared server, not just
   Airy's** — `r4-settings-tree.txt` lines 27-46: the "Database" combobox lists 18 options
   (`The shared database`, `airy_db`, `airy_db_dev`, `airy_panel_dev`, then unrelated
   `HiveCafeCoDev`, `HiveEvilDev`, `HiveVintusDev`, `dnd_db`, `evil_dash_db`, `evil_dash_dev`,
   `evil_money_db`, `evil_money_dev`, `hive_cookie_cream`, `hive_directory(_dev)`,
   `hive_operator(_dev)`, `hive_warden(_dev)`) with no grouping and no visual separation of
   "Airy's own" from "every other app on this box". A mis-click one row off points a bot's data at
   an unrelated app's database with no warning. Fix: show only the Airy-relevant entries by
   default (shared, airy_db, airy_db_dev, airy_panel_dev), or group the rest under a clearly
   separate "other databases" heading.

### Low / Nit

5. **Two different commit-row shapes for the same "discard edits" action** — the Settings page
   footer reads "Undo changes" / "Save" with no count (`r4-settings-1440.png`), while the Commands
   editor footer reads "No changes" / "1 changed" with "Cancel" / "Save"
   (`r4-editor-1440.png` vs `r4-editor-changed-1440.png`). Same job, different verb ("Undo" vs
   "Cancel") and only one of the two states a change count. Fix: one commit-row component, one
   wording, used both places.

6. **Avatar image clipped by 2 px** — `r4-look.json`, 1440, `probe.overflow`:
   `{"kind":"clipped-y","by":2,"sel":"span.avatar","rect":[297,243,96,96]}`, the "Now" card's
   picture. Minor rounding in the rounded-square mask, not visible without the probe. Fix the
   container's overflow math; low priority.

## Measured, explained, not counted as new findings

- axe: 0 violations at every width on every page (`r4-commands.json`, `r4-settings.json`,
  `r4-channels.json`, `r4-look.json`).
- Phone widths (320/375) report 0 real probe findings on Commands and Settings, and the only
  boxes on Channels/Look at 375 are hidden 1x1 native inputs whose wrapping `LabelText` is the
  real target (`r4-channels-375-legend.md`, `r4-look-375-legend.md`) — same pattern already
  cleared in R3.
- The ten 36x20 feature switches on Commands and the per-channel Pause switch on Channels all
  measure a real hit rectangle of 44x28 in the probe JSON (`"hit": [44, 28]`), above this series'
  24 px desktop floor; the small drawn box is not the clickable area. This is the fix for R3 High
  #1.
- The 13-15 px "SMALL FIELD TEXT" findings at 1440 (search placeholders, the bot switcher) are the
  16 px rule, which is phone-only; not applicable at this width.
- The boxed-off emoji (Success emoji field and its quick-pick row in the Counting editor,
  `r4-editor-1440.png`/`-375.png`) are the stated headless-browser emoji-font gap, not a defect.
- Field hint sentences stay in DM Sans, never mono, in every editor field sampled ("A wrong boss
  answer resets the count…", the Boss next message template body) — crops confirm proportional
  type for sentences and JetBrains Mono only for the standalone numbers (`300`, `0.01`) and the
  Discord application id / owner id. This matches the owner's mono-never-for-sentences rule and is
  applied correctly throughout, not only where the brief called it out.
- `r4-settings-1440-legend.md` #9/#10 "OVERLAP" is the same fact as Finding 2 (the id text under
  the sticky bar), not a separate issue.
